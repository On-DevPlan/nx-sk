# A03 — 扩展方式（四类，按改动面从小到大）

> 归属 `dev-nxsk`。原则：**先想清楚这是 action、模块、迁移，还是纯 UI**——四类的改动面和验证方式完全不同。

## 一、加一条 action（最常见的改动）

> 判据：已有模块能承载这个能力（比如「栏目/条目/附件」），只是少一个操作。

1. **声明**：在 `src/modules/<id>/index.js` 的 `actions[]` 里加一条（形状见 [[A02-模块与工程契约]] 第三节）。
   - 必须给 `cli`（否则装载期自检报「没有 CLI 命令」）；要不要 `http` 取决于面板用不用它。
   - `flags` 的类型写对：数值 `number`、开关 `boolean`、可重复 `array`、结构化 `json`。
2. **实现**：在 `src/modules/<id>/service.js` 写 `export async function xxx(ctx)`。
   - 读写 store 一律 `loadStore` / `mutateStore`；不要自己 `fs.readFile`。
   - 失败用 `core/errors.js` 的语义化错误：`notFound` / `badInput` / `conflict` / `blocked`，
     **报错要能照着改**（把「现有值」「可用值」打出来）。
3. **人读输出**：写 `render(ctx)`，`--json` 时用返回值即可。
   - 有改动就把**新旧值**打出来（「字段 phone：分组 contact → reach」），只说「已更新」等于没说。
4. **面板接线**（如果需要 UI）：在对应 `view.jsx` 里调 `api(...)`，按钮放在已有工具栏/行内操作里。
5. **测试**：
   - 单测 `tests/unit/<主题>.test.mjs`：走 service（临时 HOME），钉语义而不是钉字符串；
   - 冒烟 `tests/smoke.mjs`：加 2-3 条断言，**HTTP 与 CLI 两头各一条**（面板走 HTTP，agent 走 CLI）。

```bash
npx eslint . && node --test tests/unit/<主题>.test.mjs && node tests/smoke.mjs
```

**漏一步会怎么红**：不写 `cli` → 启动即崩；`http` 与别的路由撞车 → 启动即崩；只加 HTTP 不接线 → 面板 404。

## 二、加一个模块（改动面最大，8 步）

> 判据：这是一个**新的领域**（有自己的实体、自己的面板、自己的 CLI 组），不是某个模块的一个操作。

1. 建目录 `src/modules/<id>/`，写 `index.js`（模块声明）、`service.js`、`view.jsx`（若无面板就 `view: null` 且不建 view.jsx）。
2. **后端注册**：`src/runtime/registry.js` 的 `MODULES` 数组加一行 `import <id> from '../modules/<id>/index.js'`。
3. **前端注册**（有面板时）：`src/web/frontend/registry.js` 的 `VIEWS` 加一行
   `{ id, title, order, component: lazy(() => import('../../modules/<id>/view.jsx')) }`。
4. **eslint 互依禁列**：`eslint.config.js` 的 `SIBLING_MODULES` 加 `'../<id>/*'`——
   这一步**不会**被任何断言抓到，漏了就等于给这个模块开了「谁都能依赖我」的口子。
5. **库入口**（可选，供程序化调用）：`src/index.js` 里 `export * as <id> from './modules/<id>/service.js'`。
6. **测试**：`tests/unit/` 加一个；`consistency.test.mjs` 会自动核对目录 ↔ 注册表 ↔ VIEWS。
7. **文档**：`assets/nx-sk/SKILL.md` 的 ref 路由表 + 对应 reference（那是**用户向**文档，不是本 skill）。
8. **跑门禁**：`npx eslint . && npx vite build && node --test && node tests/smoke.mjs`。

**几个必知点**
- 模块 `id` 必须与目录名一致；`order` 决定 tab 顺序（system=100，栏目=500，条目=600，附件=650，导出=700，设置=900）。
- 模块之间**不得互相 import**（只有 `system`、`transfer` 例外）；共享逻辑下沉 `src/core/` 或 `src/shared/`。
- `resource: '<entity>'` 一旦声明，一致性测试就要求 `list/get/add/update/remove` 五个 action 齐备且两端可调用。

## 三、加一次 store 版本迁移

> 判据：**已落盘的数据形状变了**（字段改名、结构换了、旧概念作废）。

1. `src/core/store.js`：`STORE_VERSION` +1，新写一个 `migrateXxx(store)`（幂等：只在 `oldVersion < N` 时跑）。
2. 迁移里**不动用户数据**能不动就不动：不再显示的键 ≠ 删掉（`27 处`的真实事故就是这么来的）。
3. `loadStore()` 已经替你做了：**迁移前把原始 store 整份快照**到 `migrationDir()`，
   并把「迁移了什么」记进 `migrationNote()`（bootstrap 会展示给用户）。
4. 单测：造一份**旧版本**的 store 文件 → `loadStore()` → 断言迁移后的形状 + 快照文件存在 + 再跑一次不重复迁移。

```js
// 形状参考（src/core/store.js）：只在 oldVersion < N 时执行，返回「迁移摘要」给 migrationNote
function migrateKvToTable(store, oldSettings) { /* … */ return { section, fieldsBefore, fieldsAfter, movedValues }; }
```

**别做**：把迁移写成「每次读都跑一遍」——归一化（`normalize`）负责**兼容读**，迁移只负责**一次性换形状**。

## 四、加一个面板交互（纯前端）

> 判据：数据与 action 都齐了，只是面板上没有入口 / 手感不好。

1. 组件放 `src/web/frontend/components/`（通用）或 `src/modules/<id>/` 下（模块专属，如 `kvTable.jsx`）。
2. 状态：跨页面选择放 `store.jsx` 的 `ui`（会持久化）；纯局部状态用 `useState`——**别把数据塞进 ui 缓存**。
3. 样式只加到 `src/web/frontend/styles.css`（没有 CSS Modules），用 `:root` token，别写死颜色。
4. 交互反馈三件套：`toast()`（结果）、`guard()`（包异步、失败自动 toast）、`dialog()`（危险操作确认）。
5. 可访问性：可点元素用 `<button>`；拖拽必须有非拖拽入口（`选择文件` / 上移下移按钮）。
6. 无 emoji；字体、间距、圆角走 token。

## 五、四类改动对照表

| 改动 | 动哪里 | 验证 |
| --- | --- | --- |
| 新操作 | `modules/<id>/index.js` + `service.js`（+ `view.jsx`） | 单测 + 冒烟双端 + `routes` |
| 新模块 | 上述 + `runtime/registry.js` + `web/frontend/registry.js` + `eslint.config.js` + `src/index.js` | `consistency.test.mjs` 全绿 |
| 数据形状变了 | `core/store.js`（版本/迁移/归一化）+ 受影响 service | 迁移单测（旧 store → 新形状） |
| 只改手感/视觉 | `web/frontend/*` + `styles.css` | `vite build` + 逐页截图（含窄屏） |

## 六、收尾清单

- [ ] `nx-sk routes` 能看到新 action（CLI 与 HTTP 都在）
- [ ] `nx-sk help` 分组里出现（`summary` 写得像命令说明，不写「TODO」）
- [ ] 面板上的入口存在，且**失败时**给出可操作的报错（不是「操作失败」）
- [ ] `CHANGELOG.md` 记一条（用户可见的行为才算）
- [ ] `assets/nx-sk/references/*.md`（用户向文档）同步——它是 agent 填数据时的说明书
