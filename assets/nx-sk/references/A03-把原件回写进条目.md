# A03 · 把原件回写进条目（source ↔ 字段双向同步）

> 用户丢来邮件 / 截图 / PDF 摘录 / 手抄表，让你「整理进某个条目」时走这条线。
> 目标条目都还没定 → 先走 A02；PDF 要变成图文 SOP → 走 A07。

## 三条铁律

1. **原文不改写**：袋里是原始证据，整理结果写进字段（或新条目），不就地改写原件。
2. **不确定就留空**：拿不准的值不写字段，把猜测写进该条 `note`。
3. **敏感内容不进袋**：袋是明文；密码 / token 走场景条目模板的 `sensitive` 字段或 `secret`。

## 铁律第 0 条：文件先入袋，再谈整理

`source add --file` 把原件收进袋 → 它是溯源锚点（cleanup 不删、导出随包走、`file get` 能反查）。
先抄内容、原件随手一放，这三重保护都不存在。

## 五步

```bash
nx-sk status                                   # ⓿ 落点就是默认条目？
nx-sk source list                              # ① 找落点
nx-sk source add <条目> --text "原文…" --name "<叫什么>"
nx-sk source get <条目> --json                 # ② 读袋
nx-sk entry fields --template <条目模板> --json      # ③ 看台账，逐条映射
nx-sk entry update <条目> --data @整理.json --dry-run
nx-sk source update <条目> --id <item> --mapped <字段key>   # ④ 留痕
nx-sk entry get <条目> --json                  # ⑤ 自检
```

`<条目>` 在 `source get/add/update`、`entry update` 上可以**省略**——省略即默认条目（`status` 里那条）；
`source list` 仍是全局清单，不受默认条目影响。给别的条目回写时始终显式写名字，别让"省事"落错地方。

## 冲突：以新的为准，旧的留痕

同名即冲突：新的是当前版本，旧的标为「已被取代」但留在袋里；`--at` 记资料自身时间，
`--supersedes <旧id>` 显式取代；字段值跟着更新，旧证据不删。

## 双向同步手册（细节）

10 · 双向同步手册

> `A03-把原件回写进条目` 的详细页。**什么时候读**：袋里有东西要整理（第 3 步）、
> 或要把字段值回写进袋（第 4 步）时。

### 两种方向，先分清

| 方向 | 什么时候用 | 命令 | 结果落在哪 |
| --- | --- | --- | --- |
| **source → 字段** | 袋里有杂乱资料，要整理成结构化值 | `entry update --data` | 条目模板的**字段** |
| **字段 → source** | 字段值已确认，想留出处/回溯 | `source add --mapped` | 袋里的**新一条** |
| **标锚点**（双向闭环） | 某条资料已经整理过了 | `source update --mapped` | 该 item 的 `mapped` |

**别把三件事混成一件**：
「字段里已经填了值」不等于「袋里那条已经用掉」。
`mapped` 是**袋这一侧**的账，写在 item 自己身上——所以「哪些资料还没被整理过」永远查得出来。

### 整理前的映射表

一次整理一张表就够（写在回复里给用户过目也行）：

| item（id） | 内容摘要 | 目标字段 | 把握 | 处理 |
| --- | --- | --- | --- | --- |
| s_abc | 「VPN 账户：14611」 | vpnAccount | 高 | 写 |
| s_abc | 「Lj198900@#」 | vpnPassword | 高 | 写（sensitive 字段自动加密）|
| s_def | 截图里的一串端口号 | registry | 低 | **不写**，note 里记「疑似端口，待确认」|

「把握」这一列是纪律的核心：
- **高** = 原文直给，没有歧义 → 写
- **中** = 需要推断但只有一种解释 → 写，但在回复里点名说明
- **低** = 多种解释 / 缺上下文 / OCR 可能错 → **不写**，留空 + note 记疑点

**留空比写错好**：完整度会告诉你「这个字段还没填」，但错误的值会被当成事实一路传下去。

### 写回的形状

`整理.json`（`--data @file.json`）：

```json
{
  "vpnAccount": "14611",
  "vpnPassword": "Lj198900@#",
  "accessUrl": "https://qcloud.sicau.edu.cn/login"
}
```

键用 **field key** 或**中文标签**都认（与 `entry update --set` 同一套规矩）。
一次只改要整理的字段——`entry update` 是 PATCH 语义，没出现在 JSON 里的字段不动。

**先 dry-run**：

```bash
nx-sk entry update <条目> --data @整理.json --dry-run
```

返回 `wouldChange.fields` 是要写的字段 key、`newFields` 是这次顺带登记的新键
（字典里没有的键会自动登记，**注意看**——它常常意味着你写错了字段名）。

### 回写（字段 → source）

什么时候要回写：字段里的值是**从别处来的**（邮件、手抄、别人告诉你的），
需要在袋里留一份带出处的副本。

```bash
nx-sk source add <条目> --text "14611" --name "VPN 账号（李晶老师邮件）" \
  --mapped vpnAccount --note "整理自 vpnAccount 字段"
```

回写出来的 item 长这样（`mapped` 让它和字段互相指认）：

```json
{
  "id": "s_xyz",
  "kind": "text",
  "name": "VPN 账号（李晶老师邮件）",
  "text": "14611",
  "addedAt": "2026-10-20T…",
  "note": "整理自 vpnAccount 字段",
  "mapped": ["vpnAccount"]
}
```

**别回写敏感值**：`sensitive` 字段的明文不该出现在袋里（袋是明文的）。
密码/token 留在密文字段里，袋里只记「见〈某字段〉」。

### 标锚点

```bash
nx-sk source update <条目> --id s_abc --mapped vpnAccount,vpnPassword
```

`--mapped` 接受逗号分隔。想清掉就传空：`--mapped ""`。

`source update` **不改正文**——它只改名字、备注、锚点。
要改内容就删掉重加（`source remove` + `source add`）：
原文一旦被就地改写，「原始」这个词就不成立了。

### 冲突：以新的为准，旧的留痕

资料会**更新**：老师又发一封邮件说密码改了、同一个链接换了地址。这时候**不要覆盖、不要删**。

#### 规则

| 情形 | 判定 | 动作 |
| --- | --- | --- |
| 两条同名 | 冲突 | 时间新的 = 当前版本；旧的自动标「已被取代」，仍留在袋里 |
| 时间用哪个 | `at`（资料自身时间，如邮件时间）优先，缺省用入袋时间 | 加资料时用 `--at 2026-10-19` 写清 |
| 名字不同但同一件事 | 人工判定 | 新条加 `--supersedes <旧id>`，旧条同样被标取代 |
| 手动标记 | 任意 | `nx-sk source update <条目> --id <旧id> --superseded` |

#### 为什么「留痕」比「覆盖」重要

密码改过三次之后，**「现在的密码」和「它为什么是这个」一样重要**。
覆盖掉旧资料，就再也说不清「当时为什么发的那封邮件里写的是另一个值」——
而这类问题（密码到底哪个是对的、哪个已失效）恰恰是**事后**才会冒出来的。
所以：字段里放**当前值**，袋里留**全部版本**（旧的折叠但可查）。

#### 整理时怎么处理冲突

1. `nx-sk source get <条目> --json` → 看 `items[]`，`superseded: true` 的是旧版。
2. 写字段时用**当前版本**（没被取代的、时间最新的那条）的值。
3. 写完给用上的 item 打锚点：`source update --id <id> --mapped 字段key`。
4. 旧版**不用管**（它已经被自动标取代），但也别删。

```bash
## 又来一封邮件（同名 + 新时间）→ 新的自动成为当前版本，旧的自动留痕
nx-sk source add <条目> --text "密码改成 NewPass2 了" --name "分配邮件" --at 2026-10-19
## 字段跟着更新
nx-sk entry update <条目> --data @更新.json --dry-run && nx-sk entry update <条目> --data @更新.json
## 给新条打锚点
nx-sk source update <条目> --id <新条id> --mapped vpnPassword
```

### 查「还有哪些没整理」

```bash
nx-sk source get <条目> --json
```

然后看每个 item 有没有 `mapped`：

```bash
nx-sk source get <条目> --json | node -e "
let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{
  const j=JSON.parse(s);
  const un=(j.items||[]).filter(i=>!(i.mapped||[]).length);
  console.log('未整理:', un.length, un.map(i=>i.name||i.id).join('、'));
})"
```

### 一次性整理多个条目

袋是**按条目**分的，所以「整理一批」= 对每个条目各走一遍第 2–4 步。
批量写盘时**每个条目一次 `--dry-run`**（`entry update` 没有跨条目的批量模式）：
逐条 dry-run、逐条确认、逐条写。写错了也只错一条。



## 文件与资料怎么进袋

20 · 文件与资料怎么进袋

> `A03-把原件回写进条目` 的详细页。**什么时候读**：用户丢来的是文件、截图、PDF、
> 邮件、表格这些「非纯文字」的东西时。

### 原则：原件进附件库，袋里只留引用

```bash
nx-sk source add <条目> --file "D:\资料\用户指南.pdf" --name "平台用户指南 v1.3"
```

- `--file` 会把文件**复制**进 `~/nx-sk/files/`（原件保留在原处，不搬走），
  同内容自动去重（sha256），袋里留一个附件 id。
- 想要「原件搬进库里」那是 `nx-sk file add` 的语义（它默认移动）——两者别混。
- 袋里的 `file` item 只存 `fileId`；读的时候用 `nx-sk file get <fileId>` 或
  `source get --json` 里的 `files[fileId].path` 找物理路径。
- **袋里的文件算「已引用」**：`file cleanup` 不删它、`transfer export` 随包带走——
  袋是溯源的锚点，整理错了随时能点开原件回看。所以文件先入袋没有代价；
  不入袋的原件躺在库外，清理、移动、丢失都没有任何机制能拦。

### 各类资料的进法

| 资料形态 | 进法 | 注意 |
| --- | --- | --- |
| 截图（PNG/JPG） | `--file` | 面板里可多选一次拖一批；OCR 不准的数值**不要**直接写进字段 |
| 一段话 / 聊天记录 | `--text`（原文照抄，保留换行） | 别顺手"整理"成一段话——原文里的换行与缩进常常就是结构 |
| 一个网址 | `--url` | 网址本身可能就是信息（"这个链接是入口"）|
| 邮件 | `--text` 抄正文 + 需要的附件 `--file` | 抬头/发件人/时间写进 `--name` 或 `--note` |
| 表格 | 抄成 `--text`（制表符/逗号分隔），或整理成 `entrylist` 的行 | 表格往往就是「结构化清单」的原料，见下 |
| PDF | 抽文字后 `--text`；整份留档用 `--file` | 要图文 SOP 走 `A07-把PDF转成图文SOP`，别在这里手搓 |
| Word/Excel | 另存为 PDF 或纯文本再进 | 直接塞二进制没法读 |

### 表格 → 清单行

表格类资料常常**已经接近结构化**了。两种处理：

1. **留在袋里**（推荐先这样）：`--text` 存原文，第 3 步再决定怎么落。
   原文留着，整理错了还能回看。
2. **直接落成 `entrylist` 的行**：条目模板里有 `entrylist` 字段时，把表格的每一行
   写成一条 `{列名: 值}`（`--data` 传 JSON 数组），列在字段定义的 `fields` 里声明。

别在第 1 步就落成清单行——**先收下**是这条流程的第一原则。

### 批量进一批文件

面板最快：条目表单底部「原始资料」折叠条 → 右侧侧边栏 → 「＋ 选择文件」（可多选）
或直接把一批文件拖进左栏。

CLI 逐个加（每条一次调用）：

```bash
for f in /path/to/*.png; do nx-sk source add <条目> --file "$f" --name "$(basename "$f")"; done
```

### PDF 的两种去向

| 你要做的是 | 走哪条路 |
| --- | --- |
| 把这份 PDF 变成图文 SOP 条目模板 | `A07-把PDF转成图文SOP`（抽图、按版面挑图、建条目模板、图文步骤）|
| 只是把这份 PDF 存下来、以后当资料引用 | 本页：`--file` 进袋，留个 `--name` |
| 把 PDF 里的表格/清单抽出来整理成字段 | `A07-把PDF转成图文SOP` 的 `pdf_extract.py` 抽文字 → `--text` 进袋 → 第 3 步整理 |

### 命名怎么起

`--name` 是这条资料在清单里显示的名字（人读）。规则：**能认出是什么就行**。

- 好：`李晶老师的资源分配邮件`、`平台用户指南 v1.3`、`控制台首屏截图`
- 差：`未命名`、`1.png`、`新建文件`（认不出就没法整理，等于没分类）

### 收进来的东西要不要整理、什么时候整理

**当场不问、也不整理**：用户只是「先存着」的时候，把东西收进袋、告诉他在哪，
别顺手就整理——他可能还没想好这些资料该怎么归。

**当场整理**：用户说了「整理成表」「归档到字段」，或者资料本身很明确
（一封只包含一个地址的邮件），那就走完第 3–4 步。

**一个袋塞太多**：一个条目里堆了几十条还没整理的资料，
建议**拆成多个条目**（按主题分），或者先在袋里分好组再整理。
袋子上限是 500 条，但**超过十几条就该考虑拆条目了**——那不是袋的问题，是条目粒度的问题。
