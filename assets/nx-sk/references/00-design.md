# 00 · 设计思想（栏目 / 条目 / 字段）

> 归属 `nx-sk` skill 主文档。**想搞懂「这个工具为什么这么设计、东西该往哪儿放」时读这篇。**
> 怎么调命令看 `10-sections-entries` / `20-secrets` / `30-credentials` / `40-files` / `50-deploy` / `60-transfer`。

## 一、一句话：栏目确定结构，条目确定数据

```
栏目（section）  = 一张表的**表头**：分组 + 字段（key / 中文标签 / 类型 / 是否密文 / 填写策略）
条目（entry）   = 表里的**一行**：values{ 字段 key: 值 }
```

- **结构归栏目**：这个栏目有哪些字段，永远只有一个答案，在栏目里。
- **值归条目**：具体填了什么，只在条目里。

分开的好处是**结构改一次，所有条目跟着变**（加一个「证书」字段，八十个条目一起多一格，
不用挨个去补）；反过来，**填值永远不需要先改结构**——这是本工具的手感所在。

## 二、内置字段：开箱即用的建议清单

新栏目不从零开始：内置模板直接给出一套**该填什么**的建议字段。

| 模板 | 给你的建议字段 |
| --- | --- |
| `job` 求职 / 个人信息 | 姓名 / 学历 / 联系方式 / 求职意向 / 附件资料（约 80 个字段，10 个分组） |
| `projects` / `internships` / `campus` | 一段经历 = 一个条目，角色 / 时间 / 技术栈 / 职责各自独立成字段 |
| `secret` 密钥 | **只有一列**：键名 → 值（一行一个键值对） |
| `deploy` 部署配置 | 一份配置文件 = 一个条目：正文 / 放哪 / 哪些值要替换 / **凭据清单** / 何时用 |
| `platform` 容器平台 | 一个平台 = 一个条目：控制台链接 / 账号 / 密码 / 镜像 / 命名空间 |
| `thesis` 毕业论文 | 规范里的每条硬指标 = 一个字段（页边距 / 字号 / 图表规范 / 参考文献…） |

**模板是建议，不是合同**：字段可以改标签、可以删、可以加；栏目建出来之后就**独立演化**，
模板再变也不会偷偷改你的栏目。模板后来新增的字段用 `nx-sk section sync <栏目>` 补进来
（**只增不改不删**；面板上是「栏目 → 编辑 → 同步模板字段」）。

首次运行会**播种 6 个栏目**（求职 / 项目 / 实习 / 校内 / 密钥 / 部署配置），
另外两个模板（platform / thesis）需要时自己建。

## 三、动态栏目 + 动态条目：任何东西都能存

这个工具不预设「你的信息」长什么样。三层都是动态的：

| 层 | 能做什么 |
| --- | --- |
| 栏目 | 想加就加（`section add`），想删就删（`section remove`），能改标题、分组、顺序 |
| 字段 | 能加（`section update --add-field`）、能删、能改标签与提示 |
| 条目 | 能加、能改、能删；**每条栏目里的条目形状不同也没关系** |

**台账不拦写入**：`entry update --set 任意键=值` 一律能存，字典里没有的键会**自动登记**
（键名就是它本身，中文也可以，类型按值推断）。

> 但有一个**义务**：自动登记只保证「值存进去了」，**面板按字段字典渲染**——
> 没进字典的字段在界面上看不见。所以写完新键，要么让它自动登记成功（看返回里的
> `createdFields`），要么显式 `section update --add-field` 声明一次。

例外只有一处：**KV 栏目不许加字段**（`secret` 与它的同类）。它的形状就是「一行一个键值对」，
要加东西就用 `key set <名称> <值>`——见 `20-secrets`。

## 四、值的三种形状（外加附件）

| 形状 | 什么时候用 | 长什么样 |
| --- | --- | --- |
| 标量字段 | 一个值 | 文本 / 数字 / 日期 / 是否 / 多值标签 |
| **结构清单** `entrylist` | 一个条目挂**多组**结构（多组账号、多条链接） | 行数组，列在字段定义里声明；密码列标 `sensitive` 即密文落盘 |
| **原始资料袋** `source` | 还没整理的杂乱资料（邮件 / 截图 / 摘录） | 一袋资料条目，**先乱入、后整理** |
| **附件** `file` | 二进制原件（简历 / 头像 / 证书） | 附件 id 列表，原件在 `~/nx-sk/files/` |

「先乱入、后整理」是刻意留的：真实数据几乎不是一次填对的，没有这个袋子，
用户只有两个坏选择——把乱数据硬塞进结构化字段（把结构搞脏），或者干脆不存（信息丢了）。

## 五、聚合所有信息

结构可以无限动态，但**信息要能一眼看全**。所以有四个聚合点：

| 聚合点 | 命令 | 用途 |
| --- | --- | --- |
| 一个栏目的全貌 | `nx-sk section dump <栏目>` | 字段字典 + 全部条目 + 每个条目的完整度与**未填清单** |
| 跨栏目的凭据台账 | `nx-sk entry keys [--reveal]` | 所有栏目里的 链接 / 账号 / 密码 / 令牌 / 镜像 |
| 跨栏目的关键字段 | `nx-sk entry fields` | 模板给了什么 + 你实际写过什么（哪些键在用、哪些是死字段） |
| 整库搬家 | `nx-sk transfer export` / `import` | 一份 ZIP 带全部栏目、条目与附件引用 |

另外，**头部导航分组**（`settings.navGroups`）把同域栏目收成一个入口——
但它**只是显示配置**，不动任何栏目与条目数据。

## 六、密文边界

不是所有字段都一样：**标了 `secret` / `sensitive` 的字段落盘是 AES-256-GCM 密文**，
读出来默认是原文（自己看的东西不先拦一道），`--mask` 才打码。

- 键名像凭据（密码 / 口令 / 密钥 / 账号 / token / apiKey / accessKey…）时，
  **自动登记出来的字段直接就是密文字段**——「大胆写」不等于「明文裸奔」。
- 一条场景的凭据写在**那个场景的栏目**里；跨场景通用的 key 才进 `secret` 密钥栏目。详见 `30-credentials`。

## 七、给 agent 的三条不变量

1. **台账不拦写入，但必须登记。** `--set 任意键=值` 一律能存；没见过的键自动进字典，
   否则面板看不见（像「存了却没生效」）。
2. **面板与 CLI 是同一套业务。** 面板上能做的，CLI 都能做，参数名与错误码两端一致——
   所以「让用户在面板上点一下」和「让 agent 敲一条命令」是同一件事的两面。
3. **失败抛异常（退出码 1），业务结果返回 `{ status }`（退出码 0）。**
   `conflict` / `blocked` / `skipped` 都是**正常返回**——agent 要看 `status` 字段，
   而不是拿退出码判断失败。把「等用户决策」的冲突当成失败去重试，是这里最容易犯的错。

## 八、这份文档不写什么

代码怎么分层、接口长什么样、构建怎么跑、工具链怎么配——**那些是开发这个项目的事**，
装了包也用不上，所以不在这里（它们在项目仓库的 README 里）。
