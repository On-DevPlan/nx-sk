# A04 · 存密钥和凭据（安全 list&lt;kv&gt; / 场景凭据 / 配置渲染）

> 场景凭据写进场景条目模板，通用 key 写进 secret 的 `keys` 字段，两者都密文落盘；要配置文件时直接取真值渲染。

## 第一部分 · 密钥与密文

20 · 密钥（安全 list&lt;kv&gt;）与密文

> 归属 `nx-sk` skill 主文档。存/取大模型 API Key、排查「解不开」时读这篇。
> **场景级的账号密码不在这条线上**——它们写在场景自己的条目模板里，见 `A04-存密钥和凭据`。

### 一、模型：普通条目模板里的一个安全 list&lt;kv&gt; 字段

`secret` 是普通条目模板，里面有一个 `keys` 结构清单字段：

- **面板**：就是普通条目页 + 一张可加行的清单（名称 / 值），不是特殊「KV 表格页」。
- **CLI**：`key set/get/list/remove` 四条。
- **结构**：全部键在**一个承载条目**的 `keys` 字段里；新增键是加一行，不是新建条目。

清单长这样（值以密文落盘，读写默认给原文）：

| keys[].name | keys[].value |
| --- | --- |
| `OPENAI_KEY` | `sk-…`（密文落盘） |
| `DEEPSEEK_KEY` | `sk-…` |
| `OPENAI_BASE_URL` | `https://…` |

「这个 key 干什么用」写进名称里就够了 —— 存一个 key 不该先填一张表。
密钥字段与项目里其它内容完全同构：**字段 + 条目**，不再有 `kv:true` 模板。

#### 这份清单放什么、不放什么

| 放这儿 | 不放这儿 |
| --- | --- |
| **跨场景复用的通用 key**：`OPENAI_KEY`、`GITHUB_TOKEN`、`NPM_TOKEN`…（要 `export` 给各种工具用的那种） | **只服务于一个场景的凭据**：某台服务器的密码、某个平台的账号、某个 compose 的数据库口令 —— 它们写在**那个场景自己的条目**里（密文落盘，读的时候顺带知道是谁的） |

判断口径：**处处要用 → secret 的 keys 字段；只属于一个场景 → 场景条目模板**。
完整口径与「场景凭据怎么写、怎么渲染成配置文件」见 `A04-存密钥和凭据`。

### 二、四条命令（日常只用这四条）

```bash
nx-sk key set OPENAI_KEY sk-xxxxxxxx            # 写入：不存在则新建，存在则覆盖
nx-sk key get OPENAI_KEY                        # 取值：默认就是原文
nx-sk key get OPENAI_KEY --mask                  # 投屏/截图时才打码
nx-sk key list                                  # 列出所有键（默认原文）
nx-sk key remove OPENAI_KEY                     # 删除（不可撤销，删前先 transfer export）
```

| 命令 | 说明 |
| --- | --- |
| `key list [--mask]` | 列出清单里的全部键，按写入顺序 |
| `key get <名称> [--mask]` | 单个键的值 |
| `key set <名称> <值>` | **SET 语义**：存在即覆盖，不存在则追加一行 |
| `key remove <名称>` | 只删清单里这一行；删空后字段置空，不删承载条目 |

四条都接受 `--template <条目模板>` 与 `--entry <承载条目>`；缺省作用在 `secret` 的 `keys` 字段上。

> **`key *` 不受默认条目影响**：它找的是 `secret` 的承载条目，不是 `settings.defaultEntry`。
> 也正因如此，别为了「方便」把默认条目指到密钥承载条目上再跑 `entry update --set …` ——
> `entry update` 省略 `<ref>` 会落到默认条目，那等于绕开 `key *` 的密文边界去改清单。

#### 与 `entry` 的关系（重要）

`key *` **不是第二套实现**，是 `entry *` 的语法糖：它把「哪个条目模板 + 哪个值字段」定好，
再走同一套读写流程。所以加解密、`--dry-run` 的行为只有一种，不可能分叉。

等价关系：

```
nx-sk key set OPENAI_KEY sk-xxx
  ≡ 在 secret 的承载条目里更新/追加 keys 行 { name: 'OPENAI_KEY', value: 'sk-xxx' }

nx-sk entry update 密钥 --template secret --set 'keys=[{"name":"OPENAI_KEY","value":"sk-xxx"}]'
```

作用在哪个字段？**默认只认 id 或标题为 `secret` 的条目模板**；它里面有 `keys` 结构清单就用
field 模式，只有旧单值 `value` 字段则退回 legacy 模式。自建密钥模板不会被自动认领，
要显式 `--template mykeys`；没有条件时也先加 `--entry` 指定承载条目，避免多个同类条目歧义：

```bash
nx-sk template add mykeys --preset secret   # 从密钥预置建：普通模板 + keys 字段
nx-sk key set OPENAI_KEY sk-xxx --template mykeys
nx-sk template list                          # 不再有 KV 标记
```

#### 旧数据仍按「一条一键」读写

已有旧库存（模板只有一个 `value` 密文字段、每个键一条条目）时，`key *` 自动走 legacy 模式：
仍然按条目标题 = 键名读写，不自动迁移、不删除。新代码不再创建这种形状。

要彻底收敛成「一个条目 + 一个 `keys` 清单」，显式跑一次迁移（先备份；`--dry-run` 只算不改）：

```bash
nx-sk key consolidate --dry-run
nx-sk key consolidate
```

它会把旧单值条目解密后再按新密文边界重新加密到清单行里，公共空白容器本身转成承载条目，
树上最终只剩一个节点；重复跑是幂等的。

#### 两个刻意的语义差别

| | `entry add` | `key set` |
| --- | --- | --- |
| 遇到重名 | 报 `CONFLICT` | **静默覆盖**（key 的 SET 就是覆盖） |
| 返回值 | — | `created: true/false`，调用方据此知道是哪一种 |

另外两点：

- **值以 `-` 开头时**用 `--value=<值>`（`key set K --value=--x`）——`--x` 会被当成 flag。
  显式 flag 覆盖位置参数，两种写法等价。
- **重复写同一个值不会重写密文**：返回 `{ status: 'skipped', unchanged: true }`。
  每次加密都用新 IV，无脑重写只会产生一堆无意义的新密文。

#### 多行值：走 stdin 或 `@文件`（真实事故）

Windows 上命令经启动器转发时，**命令行参数里的换行会被截断**，而命令**照样报成功**——
一次性凭据（多行私钥、恢复码、证书）就这么静默丢掉后半截。同一条通道还会让含 `<` `>`
的参数整串失败（被当成重定向符，报「系统找不到指定的路径」）。

值的可靠通道有两条，任选：

```bash
printf '%s' "$KEY" | nx-sk key set OPENAI_KEY -        # stdin：值的位置参数写 -
nx-sk key set OPENAI_KEY --data @C:/Users/me/值.json    # 文件：--data @路径（含 value 键）
```

`--data` 也接受 `-`（从 stdin 读 JSON）与直接给 JSON 字面量；对象含 `value` 键时取它，
只含一个键时取那个键，多键且无 `value` 直接报错（不猜）。

**路径必须用 Windows 形式**（`C:/Users/...`）：Git Bash 的 `/tmp` 在 node 侧看不到
（实测 ENOENT），node 侧拿到的会是 `D:\tmp\...` 这种对不上的路径。

##### 哪些情况下命令行参数本身是安全的

实测（Windows 11 · Volta · Git Bash）分两种情况，**别当成一回事**：

| 你在哪敲 | 命令行多行参数 | 说明 |
| --- | --- | --- |
| **Git Bash / WSL 终端** | ✅ **安全** | 0.3.4 起转发器直连真实 `node.exe`，绕开了会截断参数的那一跳 |
| **cmd.exe / PowerShell** | ❌ **损坏** | 瓶颈是 cmd 解析 `.cmd` 文件内容（`%*` 展开），换 node 也治不了 |

所以：**cmd / PowerShell 下多行值一律走 `-` 或 `@文件`**，这是硬要求；
Git Bash 下裸参数已经能用，但脚本里要可移植的话，仍然推荐上面两条通道。

> 没有「检测到损坏就报错」这回事——**做不到**。损坏后的值里 CR 是被**删掉**而非保留
> （`$'a\rb'` 实际落盘 `"ab"`），所以「含 CR 即损坏」既抓不到真实损坏（零真阳性）、
> 又会拦住用 `@文件` 写入的**合法 CRLF 多行值**（高假阳性）。而 LF 截断后与一个合法的
> 单行值完全不可区分。可靠信号不存在，因此只能「提供可靠通道 + 修好通道本身」，
> 不能靠事后检测兜底。

### 三、密文机制

- 算法 **AES-256-GCM**。每个值独立 IV，带认证标签。
- 落盘的密文对象（**明文绝不进 store.json**）：

```json
{ "v": 1, "alg": "aes-256-gcm", "kid": "9f3a1c07be22", "iv": "…", "tag": "…", "ct": "…" }
```

- `kid` 是**密钥指纹**（密钥 sha256 前 12 位）。换过密钥来源时给出明确报错，而不是解出乱码。

#### 读出来是原文，落盘才是密文

**默认原文**：本机单人工具，数据是给自己看的。默认打码等于每次取值都先拦自己一道，
所以现在**不拦**——`key get` / `key list` / `entry get` / `template dump` 默认都给原文。

要打码形态（投屏、录屏、截图给别人看）时显式加 `--mask`：

```bash
nx-sk key get OPENAI_KEY --mask      # sk-x******xxxx
nx-sk key list --mask
```

**导出包恒为明文，没有打码选项**（0.12.0 起 `--no-secrets` 已移除）——
要防「包被别人拿走」，用口令而不是打码：

```bash
nx-sk transfer export secret --passphrase 口令 --out secret.zip
```

打码规则：长度 ≤ 10 全部打码；否则前 4 + `******` + 后 4。

**代价要清楚**：终端里有明文、`--json` 输出里有明文、投屏时会被看到。
密码管理器那种「默认遮住」的取舍对本机自用是净成本，但对**分享**是必要的 ——
所以外发前记得加 `--mask` / `--no-secrets`。

### 四、密钥从哪来（优先级固定）

| 优先级 | 来源 | 行为 |
| --- | --- | --- |
| 1 | 环境变量 `NX_SK_PASSPHRASE` | `scrypt(口令, ~/nx-sk/.vaultsalt)` 派生。**口令不落盘**，盐落盘 |
| 2 | `~/nx-sk/.vaultkey` | 32 字节随机密钥，首次写入密文时自动生成（权限尽力设 0600） |

```bash
## 口令模式（更安全：口令不进磁盘）
export NX_SK_PASSPHRASE='你的长口令'
nx-sk key get OPENAI_KEY

## 本机密钥文件模式（默认，零配置）
nx-sk key set OPENAI_KEY sk-xxxxxxxx
```

**同一份密文只能由同一个密钥解开**，所以换口令 / 删 `.vaultkey` 都会让旧密文报
`BLOCKED`「当前密钥与写入时的密钥不一致」——这是设计如此，不是 bug；改回去就能解开。
因此：**密钥文件要跟数据一起备份**，或者用口令模式并把口令记在别处。

查看当前来源：`nx-sk bootstrap --json` 的 `vault` 字段。

### 五、纪律（写给 agent）

- 默认原文是给**你自己看**的，也是给**你写的脚本**用的（渲染配置、导出模板时要用真值）。
  一旦要把输出交给别人（日志、issue、截图、贴给第三方），先加 `--mask`。
  （`--no-secrets` 已移除：导出包里恒为明文，要防「包被人拿走」用 `--passphrase` 整包加密。）
- **本机落盘 + 不推送 git = 安全**，不必再自我审查一遍密码本身。
  真正的边界只有三个出口：① 推送到 git / 上传云端；② 打进日志或交给第三方；
  ③ 导出包外发（包是明文）。见 `A04-存密钥和凭据` 的「第二部分 · 凭据自动化」。
- 导出文件里 `withSecrets` 字段会明确标出这份文件含不含明文 —— **外发前先看这个字段**。
- 用户想「把密钥同步到云端」——做不到，也别假装能做到。nx-sk 只在本机落盘与本地导出。

### 六、写入防呆

| 情况 | 行为 |
| --- | --- |
| 值含 `******`（打码占位）且**不等于**当前值的掩码 | 报 `INVALID_INPUT` 拒绝 —— 那多半是把打码串当成了新值 |
| 值**恰好等于**当前值的掩码（面板原样回传） | 视为「不修改」，保留原密文 |
| 值为空 | 报 `INVALID_INPUT`（空密钥没有意义；要清空请用 `key remove`） |

### 七、排查「解不开」

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `BLOCKED 当前密钥与写入时的密钥不一致` | 换了口令，或删了 `.vaultkey` | 改回原来的来源（旧口令 / 恢复密钥文件） |
| `BLOCKED 解密失败：密文已损坏，或密钥不正确` | store.json 被手工改过 / GCM 认证失败 | 从之前 `transfer export` 出来的包重新导入 |
| `.vaultkey` 不见了 | 被系统清理或误删 | 有口令模式的盐文件 `.vaultsalt` 与口令还能救；否则密文不可逆 |

**密文不可逆是特性，不是缺陷** —— 代价是「忘记密钥 = 数据丢失」，
回报是「store.json 泄露不等于凭据泄露」。


## 第二部分 · 凭据自动化（场景凭据 → 可用配置）

30 · 凭据自动化（场景凭据 → 可用配置）

> 归属 `nx-sk` skill 主文档。**要存账号密码、要把凭据变成配置文件时读这篇。**
> 密文机制本身见 `A04-存密钥和凭据`（密钥部分），字段与命令见 `A01-填一条信息`。

### 一、模型：凭据跟着场景走

**一条原则**：凭据存在**它所属的场景**里，不要为了存它去动全局「密钥」条目模板。

| 凭据 | 归属 | 形状 |
| --- | --- | --- |
| 某个云平台 / 容器平台的账号密码 | 该平台所在的条目（`platform` 模板，或自建条目模板） | 普通字段（密码列密文） |
| 某个部署场景的仓库令牌 / 数据库密码 | 该场景的 `deploy` 条目（自带「凭据清单」字段） | 结构清单（一行一组） |
| 跨场景复用的 API Key（`OPENAI_KEY`…） | `secret` 的 `keys` 字段（安全 list&lt;kv&gt;） | 一行一个键值对 |
| 简历 / 证书原件 | `job` 条目模板的 `file` 字段 | 附件 id 列表 |

为什么这么分：**凭据的寿命跟着场景**。场景下线了凭据跟着删；场景换了凭据只改一处。
把所有凭据堆进一个清单，时间一长就分不清「这条是给谁的」——
到那时唯一的办法是给键名加前缀（`aliyun_prod_password`），那等于把场景结构塞进了键名里。

**`secret` 的 keys 清单仍然有用**：它的定位是「环境变量表」——那些要 `export OPENAI_KEY=…` 的通用 key。
判断口径：**这条凭据只服务于一个场景 → 场景条目模板；处处要用 → secret 的 keys 字段。**

### 二、三种写法（按需要挑，不必都学）

#### 1. 直接写（最常用）——键名像凭据就自动加密

```bash
nx-sk entry update "阿里云" --template deploy --set 账号=ops@example.com --set 密码='P@ss…'
```

- 键名**在台账里没有**就自动登记；**键名像凭据**（密码 / 口令 / 密钥 / 账号 / 帐号 / 凭据 /
  token / apiKey / accessKey / secretKey / password / passphrase…）就**建成密文字段**。
- 结果：落盘是 AES-256-GCM 密文（`store.json` 里看不到明文），读出来默认原文。
- 不像凭据的键（`技术博客`、`端口`）仍然是普通文本字段 —— 不会把整个条目模板加密成噪音。

**这就是「大胆写」的实现方式**：不需要先声明 schema，密码也不会明文裸奔。

#### 2. 显式声明密文字段（要固定形状、要出现在面板表单上时）

```bash
nx-sk template update deploy --add-field '{"key":"registryToken","label":"仓库令牌","type":"secret","group":"cred","hint":"推镜像用的 token"}'
nx-sk entry update "阿里云" --template deploy --set registryToken=xxxxxxxx
```

`type: 'secret'` 与 `sensitive: true` 等价（后者可用于任意类型）。
面板会把它渲染成密码框并默认显示原文，可勾选「打码显示」。

#### 3. 结构清单（一个场景多组账号 / 一份配置多套凭据）

```bash
## 自建条目模板：先建条目模板，再声明「凭据清单」字段
nx-sk template add mycloud --title "我的云平台"
nx-sk template update mycloud --add-field '{"key":"creds","label":"凭据清单","type":"entrylist","group":"main","fields":[{"key":"name","label":"名称"},{"key":"user","label":"账号"},{"key":"pass","label":"密码","sensitive":true},{"key":"token","label":"令牌","sensitive":true},{"key":"note","label":"备注"}]}'

nx-sk entry update "阿里云" --template mycloud --data '{"凭据清单":[{"名称":"控制台","账号":"ops","密码":"P@ss…"},{"名称":"镜像仓库","账号":"ci","令牌":"tok-…"}]}'
```

> `deploy` 预置**自带**这个字段（分组「凭据」），直接用即可；
> 老条目模板用 `nx-sk template sync deploy` 补上。`--add-field` 遇到**同名**字段会报冲突 ——
> 那说明这个条目模板已经有了，换个 key 或删了重加。

- 行里的列名**用 key 或中文标签都认**（`密码` 与 `pass` 等价）；写错的列当场报错，不静默丢。
- 声明 `sensitive: true` 的列与顶层敏感字段同一条边界：密文落盘、`--mask` 打码。

### 三、跨条目模板台账

凭据散在各个条目模板里，用这一条命令对账：

```bash
nx-sk entry keys                          # 全部条目模板；值默认打码
nx-sk entry keys --reveal                 # 明文（喂脚本 / 给自己看）
nx-sk entry keys --template deploy         # 限定条目模板
nx-sk entry keys --q 密码                 # 关键字过滤（条目模板/条目/字段/值）
```

命中规则：字段 key / label 命中「链接 / 账号 / 密码 / 令牌 / 镜像」启发式，
或字段类型是 `secret` / 标了 `sensitive`。值策略：链接类明文、账号密码令牌类打码（`--reveal` 才出原文）。

**改密码 / 找入口 / 迁移机器前，先跑一遍 `entry keys`** —— 少一把就少一个惊喜。

### 四、把凭据渲染成配置文件（主用途）

用户要 compose / k8s / .env / Dockerfile 时，**直接给成品**，不要只给模板让人自己填。

#### 标准流程

```bash
## ① 取真值（密文字段自动解密；--mask 反而会挡住你）
nx-sk entry get "阿里云" --template deploy --json > /tmp/e.json

## ② 渲染：模板正文里的 ${VAR} 用这个场景的凭据替换
node assets/nx-sk/scripts/render-config.js /tmp/e.json ./docker-compose.local.yml

## ③ 真值副本另存一份 .env（同样不进 git）
```

#### 模板（进 git）与实例（不进 git）的分工

| | 内容 | 去处 |
| --- | --- | --- |
| **模板** | `content` 正文里写 `${VAR}` 占位；`vars` 列出每个变量该填什么 | 可复用、可分享、进仓库 |
| **实例** | 占位符换成本场景真值 | 本机文件，**不进仓库** |

`content` 是**会被复制进别人项目**的东西，所以里面只放占位符；
真值放在同一个条目的「凭据清单」里（密文落盘），出实例时现场替换。
这不是「怕明文」，是**模板与实例本来就是两种东西**。

#### 仓库里该怎么提交

```bash
## 提交的：占位符版本 + 示例
docker-compose.yml        # 里 ${REGISTRY_TOKEN} / ${DB_PASSWORD}
.env.example              # 键名齐全，值留空
## 不提交的（.gitignore 里盖住）
.env
docker-compose.local.yml
```

`.gitignore` 至少盖住：`.env`、`.env.*`（但放行 `.env.example`）、`*.local.yml`、
以及 nx-sk 自己的 `store.json` / `.vaultkey` / `.vaultsalt`。

### 五、安全边界：只有三个出口

本机单人工具，密文落盘、面板只听 `127.0.0.1`、数据在仓库之外。
所以「敢不敢大胆写」的答案取决于**这三个出口有没有开**：

| 出口 | 判断 | 动作 |
| --- | --- | --- |
| **推送到 git / 上传云端** | 真值进了版本库 = 凭据公开 | 仓库里只放占位符 + `.env.example`；真值文件加进 `.gitignore` |
| **打进日志 / issue / 聊天 / 给第三方的输出** | 明文离开本机 | 输出前 `--mask`，或手工替换；导出包外发必须 `--passphrase` |
| **导出包外发** | 包里是**明文凭据**（没有打码导出选项） | `nx-sk transfer export <条目模板> --passphrase 口令` 整包加密，只发给可信对方 |

没开这三个出口时，**不必再自我审查一遍密码本身**：
本机文件里带真值是正常的，`--mask` 是给「投屏 / 截图 / 贴给别人看」用的，不是给「自己用」用的。

### 六、常见场景怎么放

| 场景 | 放哪 | 大致写法 |
| --- | --- | --- |
| 云平台（阿里云 / 腾讯云 / AWS） | 自建条目模板「云平台」，或 `platform` 模板 | `--set 账号=… --set 密码=… --set AccessKeyId=… --set AccessKeySecret=…`（后两个自动加密） |
| 容器平台（KubeSphere / Rancher） | `platform` 预置 | 控制台链接 / 账号 / 密码 / 命名空间 / 镜像 |
| 镜像仓库 | `deploy` 条目的凭据清单 | 名称 `registry`、账号、令牌 |
| 数据库 / 中间件 | `deploy` 条目的凭据清单 | 名称 `mysql`、账号、密码 |
| 大模型 API | `secret` 密钥条目模板 | `nx-sk key set OPENAI_KEY sk-…`（跨场景复用） |
| CI / 发布凭据 | `deploy` 条目的凭据清单 | 名称 `ci`、账号、令牌 |

### 七、排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 写进去的值在 `store.json` 里能搜到明文 | 键名不像凭据（`pwd` 之外的自由词） | 声明一个密文字段重写，或把键名改成带 `密码/token/口令` 的 |
| `BLOCKED 当前密钥与写入时的密钥不一致` | 换了口令 / 删了 `.vaultkey` | 见 `A04-存密钥和凭据` 的「第一部分 · 密钥」 |
| 值被拒：「收到的是打码占位而非明文」 | 把 `--mask` 后的串写回去了 | 传完整值，或什么都不传（= 不修改） |
| 面板里看不到刚写的字段 | 字段没进台账（老条目模板 + 模板后加） | `nx-sk template sync <条目模板>` |
| 渲染出来的配置里 `${VAR}` 没替换 | 凭据清单里的「名称」与占位符名不一致 | 名称对齐（`${REGISTRY_TOKEN}` ↔ 名称 `REGISTRY_TOKEN`） |
